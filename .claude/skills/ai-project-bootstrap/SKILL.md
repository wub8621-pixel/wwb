# AI 项目启动器

## 这个 skill 解决什么

把一次「从零做项目」的对话变成**有固定节奏的流程**：先定位项目，再选框架，再谈配置，
最后交一份能让你自己调参的说明书。核心不是替你决定，而是**把每个决定都交给你**，
同时保证代码里没有藏在角落里的魔法数字。

## 硬性规则

违反任何一条都算没做完：

1. **先问项目名称，再动任何文件。** 名称决定目录，目录决定一切。
2. **新建还是更新，必须给出判断依据**（看到了哪个文件），不能靠感觉猜。
3. **所有可调参数进 `config/settings.yaml`**。业务代码里出现魔法数字就是返工。
4. **密钥只存环境变量名**（如 `api_key_env: ANTHROPIC_AUTH_TOKEN`），绝不在对话或配置里写明文。
5. **交付必须包含节点表和可调参数表**，每一项都要带 `文件:行号`。
6. **每次改动配测试并跑通**；项目里有 `AGENTS.md` / `CLAUDE.md` 时，其规则优先于本 skill。

## 流程

### 第 0 步：项目定位（先问，不要猜）

用一次 `AskUserQuestion`（最多 2 个问题）问清楚：

- **项目名称**：给 2～3 个候选名，允许 Other 自定义
- **项目根目录**：当前目录 / 常用工作区 / 自定义

然后按下表判定，**把结论和依据明确告诉用户**：

| 现象 | 判定 | 动作 |
|---|---|---|
| 目录不存在 | 新项目 | 创建目录 |
| 目录存在但没有代码文件 | 新项目 | 复用空目录，提醒用户 |
| 有 `.git` / `pyproject.toml` / `package.json` / `src/` / 多个源码文件 | 既有项目 | 进入更新模式 |
| 目录存在但特征模糊 | 拿不准 | 列出目录内容，问用户 |

**新项目**：建目录 → `git init`（先问，别擅自）→ `.gitignore` → README →
`config/`、`tests/` → 再进入第 1 步。

**更新项目**：先 `ls` + 读 README/依赖清单，摸清现有约定（包名、测试框架、配置方式），
**沿用既有约定**。禁止覆盖已有文件、禁止重排目录、禁止顺手「重构」。

### 第 1 步：框架选择

一次 `AskUserQuestion`，选项按推荐度排序，每个选项说清代价：

| 选项 | 适合 | 代价 |
|---|---|---|
| LangGraph（推荐） | 流程/状态机清晰、需要分支与回退 | 要设计 State 与 reducer，学习成本中等 |
| 纯 SDK 手写 | 链路短、想完全可控 | 分支、重试、持久化都要自己写 |
| 其他（Other） | 用户有特定框架 | 先确认其版本与关键 API |

选 **LangGraph** 时，必须先和用户对齐三件事，再写代码：

1. **State 里放什么**，哪些字段需要用 reducer 合并（并行分支）
2. **节点粒度**：一个节点 = 一件可独立重试的事
3. **边**：哪些是静态边，哪些是条件边，条件由谁判断（规则还是模型）

### 第 2 步：配置访谈（分批，别一口气问 20 个）

每轮 `AskUserQuestion` **最多 4 个问题**，总共不超过 3 轮。
**每个问题都要给推荐默认值**，用户可以直接选默认。

**A 轮 · 模型与调用**
- 模型供应商与模型名（如 DeepSeek / Claude / OpenAI）
- 密钥的环境变量名（不是密钥本身）
- 输出上限 `max_tokens`、重试次数、超时
- 是否需要结构化输出（JSON）与失败兜底策略

**B 轮 · 运行与图**
- 图的最大步数 / 递归上限
- 是否需要 checkpoint（断点续跑）
- 并发度、日志级别
- 是否需要 Web 服务及端口（若需要，补：上传大小上限）

**C 轮 · 业务参数（按项目类型追问）**

RAG / 检索类必问：
- 切分：`chunk_size`、`chunk_overlap`
- 检索：`top_k`、相似度阈值、是否混合检索
- 融合策略：RRF / 加权 / 直接拼接；融合参数
- 重排：是否启用 rerank、rerank 模型、保留条数
- 工具：是否允许调用工具、允许哪些、**单轮最大工具调用次数**、总循环上限

评分 / 判定类必问：
- 维度与权重、阈值档位、硬门槛
- 是否允许模型给最终结论（默认：不允许，由规则算）

**访谈纪律**
- 用户不确定时，写进配置并加注释 `# TODO: 待确认，当前取默认值`
- 不让用户复述 API Key；只记环境变量名
- 问完一句话复述「我理解你要的是…」，确认后再落盘

### 第 3 步：落配置

固定结构：

```
config/
├── settings.yaml          # 唯一事实来源，分组 + 注释
├── settings.local.yaml    # 可选，本机覆盖，加入 .gitignore
└── loader.py              # 类型化读取 + 校验，启动即失败
```

规则：

1. **分组**：`model` / `runtime` / `graph` / `rag` / `tools` / `web` / `scoring`
2. **每个键一行注释**，写清楚「改大会怎样、改小会怎样」
3. **代码只通过 loader 取值**，禁止 `os.environ[...]` 散落在业务代码里
4. **加载即校验**：缺键、类型错、范围越界 → 启动时报错，不要带着坏配置跑
5. **不用环境变量覆盖所有配置**，只覆盖密钥、机器相关项（路径、端口）
6. `settings.local.yaml` 深合并覆盖，便于本机调参而不污染仓库

最小 YAML 与 loader 参考实现见 `references/config-recipes.md`。

### 第 4 步：实现与测试

- 先做**最小可运行链路**（能跑通、能看见输出），再加分支和优化
- 任何函数里出现的可调数字，一律改成从 config 取
- 测试至少覆盖：配置加载成功、非法配置报错、核心节点的正常与异常路径
- 有评测脚本的项目，改参数后必须重跑评测并对比前后结果

### 第 5 步：交付报告（必须做，格式固定）

项目完成后，按 `references/node-report.md` 的模板输出两部分：

1. **框架节点表**：节点 / 职责 / 输入 / 输出 / 关键配置项 / 代码位置
2. **可调参数表**：配置键 / 当前值 / 调大调小的效果 / 代码位置

重点标出用户最可能想动的开关，例如：

- 检索融合策略（RRF / 加权）、`top_k`
- 是否调用工具、单轮工具次数、工具循环上限
- 模型温度、重试次数、超时
- 阈值与权重

每个参数都要回答：**改哪个文件哪一行、改完跑什么验证、预期会看到什么变化**。

### 第 6 步：调参闭环

用户说「把 top_k 调成 5」时：

1. 只改 `config/settings.yaml`，**不动代码**
2. 跑测试 / 评测
3. 报告前后差异；如果参数改了但行为没变，说明代码没真正读这个配置——这是 bug，要修并补测试

## 反模式（出现即返工）

- 没问项目名称就创建目录
- 目录已存在却直接覆盖
- 一口气抛 10 个问题，或没有默认值让用户自己想
- 把 API Key 写进配置、日志或对话
- 配置里塞了一堆没人读的键
- 节点表只写节点名，不写职责和可调参数
- 交付时说「已经完成」，但没告诉用户从哪调
